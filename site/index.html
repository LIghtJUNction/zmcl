PROJECT Z / MINECRAFT LAUNCHER

让启动器轻一点。
把空间留给游戏。

zmcl 用 Rust 和 Project Z 构建原生 Minecraft 启动器。把实例、资源、账号与启动流程放在清晰的小模块里，持续降低启动器自身的内存和磁盘开销。

HOW IT WORKS

把开销拆开，逐项减少。

先看程序实际保留了什么，再讨论它有多轻。

01

小核心，明确边界

no_std + alloc 核心负责解析版本、选择依赖和生成启动参数。文件、网络与系统交互由应用层处理。

02

变化时才绘制

原生界面使用 Project Z 的 zui（包名 zui-native）。收到输入或状态更新时重绘，空闲时等待事件；安装和登录按需执行。

03

资源共享，存档独立

不可变资源经过校验后进入共享存储。支持硬链接的文件系统可复用同一份内容，各实例保留自己的配置与存档。

GET STARTED

从一个实例开始。

当前可从源码构建。构建环境、系统工具和 Java 的要求在仓库文档中维护。

01 / 构建并打开
git clone --recurse-submodules \
  https://github.com/LIghtJUNction/zmcl.git
cd zmcl
cargo build --release
./target/release/zmcl gui

Rust 版本以仓库工具链为准。Linux 原生界面需要 X11/XWayland、OpenGL 和系统字体库。

02 / 创建与安装
./target/release/zmcl instance create survival \
  --version 1.21.1
./target/release/zmcl install survival
./target/release/zmcl launch survival --offline Player

示例使用明确的单机身份。在线账号通过 Microsoft 授权；应用 ID 与登录流程见使用文档。

怎样做一次可比较的测试？
  1. 固定输入。 同一台机器、操作系统、GPU/显示后端、游戏版本、mods、实例数量和网络条件，固定两个启动器的提交或发行版。
  2. 分开冷启动与热启动。 分别记录空缓存与已有缓存，至少重复多次，保留原始数据、样本数、分位数与失败情况。
  3. 按完整进程树计内存。 界面空闲时同时读 PSS、SwapPss 与 RSS；安装时同时计入下载、解压等子进程。Minecraft/Java 的内存另外列出。
  4. 按实际物理文件计空间。 可执行文件、系统依赖、缓存与游戏数据分别统计。硬链接按 inode 去重；XMCL 的共享存储也采用同样口径。
  5. 在相同功能下计算差异。 未实现的能力不能当作性能节约，没有配对数据就不计算提升倍数。
